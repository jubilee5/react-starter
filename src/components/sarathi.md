1. **`AHSP` is defined twice** (id 8, parent=`DRDO/PROD` group id 15; id 23, parent=`PROD` id 7) with two different parents and two different section_type_names ("Authority Holding Sealed Particulars" vs "AHSP"). ## 3. Post-Login Dashboard Routing — two separate implementations found

There are **two independent pieces of code** that decide "which dashboard does this role land on", and they **do not always agree**:

- `LoginContainer.js` → `handleLogin()` — fires once, immediately after a successful login.
- `Sidebar.js` → `getDashboardPath()` — recalculates the "Home" link target on every render (used whenever the user clicks the **Home** nav item).

### 3.1 `LoginContainer.js` — effective routing order

⚠️ Important: `handleLogin()` actually contains **two** `if/else` chains that both call `navigate()` (lines ~108–128, then again ~178–249). Since `navigate()` is called twice synchronously and the page is then hard-reloaded, **only the second chain's final result survives** — the first chain (which includes the `NAI INSPECTOR` + Torpedo → `/TorpedoInspector` rule) is effectively dead code. The real, effective priority order is:

| # | Condition | Route |
|---|---|---|
| 1 | `SUPER-ADMIN` role OR `isDgnai === true` | `/dgnaidash` |
| 2 | `response.data.name === 'CNS Navy'` | `/ChiefNaval` |
| 3 | `response.data.name === 'VCNS Navy'` | `/ChiefNaval` |
| 4 | `response.data.name === 'DCNS Navy'` | `/ChiefNaval` |
| 5 | `response.data.name === 'AIR(SR)'` | `/ChiefNaval` |
| 6 | `response.data.name === 'ACNS(AIR)'` | `/ChiefNaval` |
| 7 | `response.data.name === 'AIR(SM)'` | `/ChiefNaval` |

### 3.3 Conflicts between the two implementations (verified)

- **NAI INSPECTOR on a TORPEDO section**: `Sidebar.js` sends them to `/TorpedoInspector` (rule 6). `LoginContainer.js`'s *live* logic (its dead first chain aside) never has a Torpedo-inspector-specific rule — it falls through to rule 19 (`sectionCode==='TORPEDO'` → `/TORPEDODASH`). **Result: immediately after login the user lands on `/TORPEDODASH`, but clicking "Home" in the sidebar afterwards sends them to `/TorpedoInspector` instead** — two different dashboards for the same role/session.
- `LoginContainer.js` has explicit `COMMODORE API` / `CAPTAIN API` → dashboard rules; `Sidebar.js`'s `getDashboardPath()` has **no equivalent rule at all** for these two roles, so clicking "Home" for a Commodore/Captain API user falls through to the generic `/EmployeeMasters/NaiEmpProfileView`.
- `LoginContainer.js` matches Naval leadership by **exact person name** (`'CNS Navy'`, `'Upadhyay'`, `'DGONA'`, `'AIR(SR)'`…); `Sidebar.js` matches by **role constant** (`CNS`, `DOM`, `DGONA`…) combined with a second literal check. These are two different data sources (`response.data.name` vs `state.role.currentRole`) and could disagree if a person's `name` field doesn't line up with their assigned role.

## 5. Consolidated code-check findings (verified against the actual source, not guessed)

| # | File | Finding |
|---|---|---|
| 1 | `LoginContainer.js` | `handleLogin()` builds **two** separate `if/else` routing chains and calls `navigate()` in both. Only the second chain's result actually survives (the page is reloaded after it). The first chain — which includes the only explicit `NAI INSPECTOR` + Torpedo → `/TorpedoInspector` rule — is dead code. |
| 2 | `LoginContainer.js` line 232 | `sectionCode === 'Factory'` is compared against a **capitalised-only-first-letter** string, but the DB's `section_type.code` for that row is `FACTORY` (all caps, confirmed in your screenshot). Since this comparison isn't run through any normalizer, it will **never match** live data — Factory-section users fall through to the default dashboard instead of `/NaiSectionInchargeDashBoard`. |
| 3 | `LoginContainer.js` / `Sidebar.js` (`isProdInspector`) | Both files compare `sectionCode === 'Trade Section' \| 'Drawing Section' \| 'Tech-cord Section'`. The DB's actual `section_type.code` values are `TRADE`, `DRAWING`, `TECH-CORD` (short codes, all caps, no "Section" suffix — confirmed in screenshot). This rule looks like it compares the wrong field (a display *name* format instead of the *code*) and is very likely unreachable with real data in both files. |
| 4 | `roles.js` — `NAI_Officer_Incharge3` | The string value is `'NAI Officer\xa0Incharge3'` — it contains a **non-breaking space (U+00A0)** instead of a normal space between "Officer" and "Incharge3". This constant isn't used anywhere in the sidebar/routing logic that was traced, but if the backend ever sends the plain-space version of this string, a strict `===` comparison using this constant would silently fail. |
| 5 | `roles.js` | `NAI_OFFICER_INCHARGE_I` (`'NAI Officer Incharge1'`) and `NAI_Officer_Incharge1` (also `'NAI Officer Incharge1'`) are two different constants with the **identical value** — a duplicate definition under two different naming conventions. Same pattern for level 2/3 (`NAI_OFFICER_INCHARGE_II` vs `NAI_Officer_Incharge2`, etc.) |
| 6 | `roles.js` | `NHQ_ADMIN` = `'NHQ HR ADMIN'`, `NHQ_HR_ADMIN` = `'NHQ HR Admin'` (different casing), and `NHQ_ADMINN` = `'NHQ-ADMIN'` (extra "N" in the constant name, and a hyphen instead of a space in the value) are **three distinct constants that look like they should be one role**. Because `Sidebar.js` normalizes role names (uppercases + strips spaces/underscores) before comparing, `NHQ_ADMIN` and `NHQ_HR_ADMIN` end up equivalent at runtime — but `NHQ_ADMINN` (`NHQ-ADMIN`) normalizes to a **different** string and is separately hard-coded into the "grant full sidebar access like Super Admin" check in `Sidebar.js` (`hasAccess`, line ~340). Worth double-checking that `NHQ_ADMINN`/`'NHQ-ADMIN'` is really meant to have Super-Admin-level visibility across the entire sidebar. |
| 7 | `SectionCodeConsts.js` | Both `ORDNANCE` and a misspelled `ORDINANCE` constant exist. The DB only ever returns `ORDNANCE` (confirmed in screenshot), so any code branch keyed on `ORDINANCE` is dead. |
| 8 | `SidebarData.js`, `Afloat` module | `Afloat`'s `sectionType` is set to the lowercase constant `ord` (`'ordnance'`) while every other module in the file uses the uppercase DB code (`'ORDNANCE'`). This happens to still work because `normalizeSectionType()` lowercases both sides before comparing — but it's an inconsistent authoring pattern that could confuse future edits. |
| 9 | `section_type` table (DB) | `AHSP` (code) appears twice — id 8 (parent 15) and id 23 (parent 7) — with two different names/parents. Likely a duplicate data entry that should be cleaned up. |
| 10 | `section_type` table (DB) | `PH` (Proof House, id 17) and `PL` (Proof Location, id 18) both have `parent_section_type_id = 2` (`AMMUNITION`), which looks unintentional if Proof House/Location were meant to sit under `ORDNANCE` (id 1) instead. |
| 11 | `Sidebar.js` vs `LoginContainer.js` | See §3.3 — the two files disagree on the landing dashboard for `NAI INSPECTOR` + `TORPEDO`, and `Sidebar.js`'s `getDashboardPath()` has no rule at all for `COMMODORE API` / `CAPTAIN API` (present only in `LoginContainer.js`). |

None of the above are being asserted as "definitely broken in production" — they're precise, code-verified discrepancies between what the source says and what the live DB data looks like. Worth a quick confirmation with whoever owns the section-type seed data and the two routing files.

## 6. Full Nested Sidebar Tree (every menu item, every role, every section gate)

Format: `Title :: href=<route>; roles=[...]; section=[...]` (indentation = nesting level). `exclude=[...]` means those roles are explicitly blocked even if otherwise matched.

